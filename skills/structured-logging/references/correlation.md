# Trace/log correlation

The point of correlation: from one slow or failed log line, jump to the
distributed trace that explains it, and back. Both directions require
the trace context to be **on every log record**.

## The fields

W3C Trace Context defines the pieces OTel carries onto log records:

| Field | Meaning |
| --- | --- |
| `TraceId` | 16-byte / 32-hex-char trace identifier. |
| `SpanId` | 8-byte / 16-hex-char span identifier. |
| `Flags` | Trace flags (sampling decision). |

On a log line these commonly appear as `trace_id`/`span_id` (snake) or
`trace.id`/`span.id` (dotted, semconv style). Pick one convention per
fleet and make sure your backend's queries use it. Don't emit both.

## How it gets there

In most stacks you don't hand-thread trace ids. The tracing SDK +
logging integration does it:

- **Node/JS**: `@opentelemetry/instrumentation-pino` (bundled in
  `auto-instrumentations-node`) injects the active span's ids into Pino
  logs. Default keys are `trace_id`/`span_id`; they're configurable
  (e.g. to `trace.id`/`span.id`).
- **Go**: use the OTel `Log` bridge or a log handler that reads
  `trace.SpanContextFromContext(ctx)`; don't stash ids in a `context`
  value you might forget.
- **Python**: the logging instrumentation adds them to `LogRecord`
  attributes (`otelTraceID`, ...) or via the OTel logging handler.

Whichever the stack: log **from within the span's context** or the ids
won't be present. A log emitted before/after the span (or from a
different goroutine/async task without propagated context) has no trace.

## Correlation is not request IDs

They are different and often both useful:

| | Trace id | Request id |
| --- | --- | --- |
| Scope | one distributed trace, many spans/services | one inbound request to one service |
| Generated by | the trace SDK / first service | you, at the edge |
| Answers | "show me the whole path of this operation" | "show me everything this request logged" |
| Propagates via | W3C `traceparent` header | often `X-Request-Id` header |

Keep a request id if you have one, in its own field (`request.id`, say)
— don't stuff it into `trace_id`. When there's no trace (untraced
service), the request id is the fallback correlation key.

## Logging outside a request

Background jobs, startup, and cron logs have no trace context. That's
expected — don't fabricate ids. Correlate those by resource attributes
(`service.name`, a job name field) and a stable event name instead.

## Propagating context across boundaries

- HTTP: propagate the `traceparent` header (and `tracestate`). Most
  auto-instrumentation does this for inbound and outbound calls.
- Queues/events: carry the W3C context in message headers/attributes and
  continue the trace on the consumer side, or start a new trace and link
  it. See [`../../cloudevents/SKILL.md`](../../cloudevents/SKILL.md) —
  CloudEvents has distributed-tracing and partitioning extensions for
  exactly this.
- Async/thread pools: context must be explicitly propagated if the
  runtime doesn't do it; a missing propagation is the most common cause
  of "the trace stops here".

## Sampling caveat

If traces are sampled, not every log line will have a trace id that the backend has a trace for. Don't conclude correlation is broken
from a single missing trace; check the sampling config. Conversely,
logs are usually unsampled, so they can point at operations whose traces
were dropped — that's a reason to keep logs structured enough to stand
alone.

## Verifying it works

1. Enable tracing with an exporter.
2. Make one request through the service.
3. Find a log line for that request; confirm `trace_id`/`span_id` are
   present and non-zero.
4. Paste the `trace_id` into the tracing backend; confirm the trace
   exists and its spans line up with the log timestamps.

Do this once per service; it's the difference between "we have tracing"
and "we can actually debug".
