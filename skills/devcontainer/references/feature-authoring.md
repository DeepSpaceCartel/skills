# Authoring, testing and publishing a Feature

[features.md](features.md) covers what the spec *requires* of a Feature.
This file covers how to build one that works on real base images,
prove that it does, and ship it. Start from
[`devcontainers/feature-starter`](https://github.com/devcontainers/feature-starter);
[`devcontainers/features`](https://github.com/devcontainers/features)
is the best large-scale example.

## Repo layout

```text
.
├── src/
│   └── mytool/
│       ├── devcontainer-feature.json
│       ├── install.sh
│       └── NOTES.md              # optional, appended to the generated README
├── test/
│   ├── mytool/
│   │   ├── test.sh               # autogenerated test: default options
│   │   ├── scenarios.json        # named option/base-image combinations
│   │   ├── pinned_version.sh     # one script per scenario name
│   │   └── duplicate.sh          # optional: Feature installed twice
│   └── _global/                  # scenarios spanning several Features
│       ├── scenarios.json
│       └── with_node.sh
└── .github/workflows/
    ├── test.yaml
    └── release.yaml
```

Only the contents of `src/<id>/` are packaged. Anything `install.sh`
needs at build time must be inside that folder.

## Writing `install.sh`

```sh
#!/usr/bin/env bash
set -euo pipefail

VERSION="${VERSION:-latest}"            # option "version" -> $VERSION
USERNAME="${_REMOTE_USER:-root}"

# 1. Fail clearly on unsupported bases instead of half-installing.
. /etc/os-release
case "${ID}" in
  debian|ubuntu) ;;
  *) echo "mytool: unsupported distro ${ID}" >&2; exit 1 ;;
esac

# 2. Idempotent: a second run (duplicate.sh, re-layered base) is a no-op.
if command -v mytool >/dev/null && [ "${VERSION}" = "latest" ]; then
  echo "mytool already installed"; exit 0
fi

# 3. Install deps only if missing, and clean apt lists in the same layer.
if ! command -v curl >/dev/null; then
  apt-get update && apt-get install -y --no-install-recommends curl ca-certificates
  rm -rf /var/lib/apt/lists/*
fi

# 4. Resolve "latest" to a concrete version, download, VERIFY, install.
#    (Compare against a published checksum/signature, never skip.)
# ...

# 5. Per-user setup for the user who will actually work in the container.
su "${USERNAME}" -c "mytool init" || true
```

- **Read options as env vars.** The option ID is uppercased and
  non-alphanumerics become `_`, so `installTools` → `INSTALLTOOLS`.
  Always set a default in the script too.
- **Install for `_REMOTE_USER`, not root.** The script runs as root.
  `_REMOTE_USER`, `_REMOTE_USER_HOME`, `_CONTAINER_USER` and
  `_CONTAINER_USER_HOME` say who will use the result. Anything per-user
  (dotfiles, PATH entries in `~/.bashrc`, language toolchains under
  `$HOME`) belongs to that user. For PATH, prefer `containerEnv` in
  `devcontainer-feature.json`.
- **Support the bases people actually use**: Debian, Ubuntu, and the
  `mcr.microsoft.com/devcontainers/*` images at minimum. Detect the
  distro and package manager from `/etc/os-release`. Exit with a clear
  error on anything else. Alpine (musl, `apk`, no bash by default)
  needs its own branch or an explicit "unsupported".
- **Detect the architecture.** Map `uname -m` / `dpkg --print-architecture`
  to download names, and support `amd64` and `arm64` (Apple Silicon
  hosts).
- **Verify everything you download**: check a SHA-256 from the
  release's checksum file, or a GPG/cosign signature. The official
  Features do this, and it's the first thing a careful user will look
  for.
- **Resolve `latest` once** to a concrete version and log it, so build
  logs show what was installed.
- **Keep the layer small.** Clean package caches and temp files in the
  same script, since each Feature is one image layer.
- **Declare order, don't assume it.** If you need the non-root user to
  exist, set `"installsAfter": ["ghcr.io/devcontainers/features/common-utils"]`.
  If you need another Feature present, `dependsOn` it.
- **Ask for the least privilege.** Every `privileged`, `capAdd`,
  `securityOpt`, host mount or `entrypoint` you declare is forced on
  every user. Add one only when the tool can't work without it, and say
  why in `NOTES.md`.

## Testing with the devcontainer CLI

```sh
npm install -g @devcontainers/cli
devcontainer features test -p .                       # everything
devcontainer features test -f mytool -i debian:bookworm --skip-scenarios
devcontainer features test -f mytool --skip-autogenerated --filter pinned
devcontainer features test --global-scenarios-only
```

| Test type | Driven by | What it proves |
| --- | --- | --- |
| Autogenerated | `test/<id>/test.sh` | Installs with default options on `--base-image` (default `ubuntu:focal`) as `--remote-user` |
| Scenario | `test/<id>/scenarios.json` + `<name>.sh` | Specific options, base images and Feature combinations |
| Duplicate | `test/<id>/duplicate.sh` | Installing twice with different options works (idempotency) |
| Global | `test/_global/` | Several Features together |

Useful flags: `--preserve-test-containers` (keep the container after a
failure so you can inspect it), `--log-level debug`, `--filter <substr>`.

```sh
# test/mytool/test.sh
#!/bin/bash
set -e
source dev-container-features-test-lib    # provided by the test harness

check "mytool on PATH" bash -c "command -v mytool"
check "runs" mytool --version
check "owned by remote user" bash -c "[ -O \"\$HOME/.mytool\" ]"

reportResults
```

```json
// test/mytool/scenarios.json
{
  "pinned_version": {
    "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
    "features": { "mytool": { "version": "1.4.2" } }
  },
  "debian_nonroot": {
    "image": "debian:bookworm",
    "remoteUser": "vscode",
    "features": {
      "ghcr.io/devcontainers/features/common-utils:2": {},
      "mytool": {}
    }
  }
}
```

In scenarios, the Feature under test is referenced by its bare `id`.
A scenario named `foo` can have a `test/<id>/foo/` folder whose files
(e.g. a Dockerfile) are copied into the generated `.devcontainer/`.

In CI, run the autogenerated tests as a matrix of Feature × base image,
including at least `debian:latest`, `ubuntu:latest` and
`mcr.microsoft.com/devcontainers/base:ubuntu`. Run scenarios and global
tests as separate jobs. That's the `feature-starter` `test.yaml`
pattern.

## Publishing

```yaml
# .github/workflows/release.yaml
name: release
on:
  workflow_dispatch:
jobs:
  publish:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: write        # git tag per Feature release
      pull-requests: write   # docs PR
      packages: write        # push to GHCR
    steps:
      - uses: actions/checkout@<full-sha>
      - uses: devcontainers/action@<full-sha> # v1
        with:
          publish-features: "true"
          base-path-to-features: "./src"
          generate-docs: "true"
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      # then commit the generated src/*/README.md and open a PR
```

Inputs of `devcontainers/action` worth knowing:

| Input | Notes |
| --- | --- |
| `validate-only` | Schema-check `devcontainer-feature.json` without publishing. Good for PR CI. |
| `oci-registry`, `features-namespace` | Target registry and namespace; the namespace defaults to the source repo (`<owner>/<repo>`). |
| `generate-docs` | Builds each `README.md` from the JSON plus `NOTES.md`. |
| `disable-repo-tagging` | Skips the git tag the action creates for each Feature release. |
| `devcontainer-cli-version` | Pins the CLI the action uses. |

- **Bump `version` in `devcontainer-feature.json`** for every change
  (semver). The publisher skips versions that already exist, and moves
  `:1`, `:1.2` and `:latest` to point at the new one.
- **Make the GHCR packages public** (each one starts private), unless
  the Feature is meant to stay internal. Private Features in Codespaces
  need `customizations.codespaces.repositories` granting `packages: read`.
- **Publish only from CI on `main`**, never from a laptop. That's half
  of what makes a Feature trustworthy to others (see
  [using-features.md](using-features.md#trust-tiers)).
- To appear on containers.dev, open a PR adding your collection to
  `collection-index.yml` in `devcontainers/devcontainers.github.io`.
- Renaming or retiring a Feature: use `legacyIds` / `deprecated`, see
  [features.md](features.md#renaming-or-deprecating-a-feature).

## What NOT to do

- Don't `curl | sh` an installer, and don't download a binary without
  verifying it.
- Don't install per-user tooling into `/root` when `_REMOTE_USER` is
  someone else.
- Don't assume Debian, amd64 or bash without checking. Fail loudly
  instead.
- Don't declare `privileged` or a host socket mount "just in case".
- Don't republish changed content under an existing version. Bump it,
  or lockfile users will see an integrity mismatch.
